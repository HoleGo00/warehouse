# 仓储领用与飞书库存同步 V1

## Goal

建设一套面向内部员工与仓库管理员的领用管理网页，覆盖正常领用、临时领用、线下登记、一道审核、发放、补手续、库存流水与查询，让高频临时领取可以先完成实物交付，同时保证每一次库存变化均可追溯，并以现有飞书多维表格库存数据作为最终库存底账。

## Background

- 当前只管理智能指环和智能腕表两个商品大类。
- 当前实际仓库为西湖仓和余杭仓，库存必须按仓库独立核算与查询。
- 智能指环需要区分具体款式和 6# 至 13# 尺码；一张指环领用单可包含多个款式和多个尺码。
- 智能腕表当前正式可申领产品只有健康腕表，但必须预留后续新增腕表产品线的能力；腕表不区分尺码，另有三个只用于历史库存保留的停用产品。
- 现有飞书资产是两套独立的多维表格：腕表库存管理与指环库存管理，均已通过用户提供的实际 URL 使用 `lark-cli` 完成只读解析、结构检查和全量记录快照。

## Requirements

### R1. 商品模型与库存底账

- 飞书多维表格是最终库存底账。
- 商品模型必须支持“大类 → 产品/款式 → 可选规格”的层级，不能把现有商品硬编码在业务逻辑中。
- V1 商品大类固定为智能指环和智能腕表，但后台数据结构应允许后续新增产品/款式。
- V1 智能指环正式产品目录包含 10 款：
  - 岁月礼赞·磨砂玫瑰金
  - 商务精英·间金昆仑灰
  - 御路荣升·蓝宝石星空
  - 巴黎经典·星钻永恒玫瑰金
  - 领袖江山·指定乾坤钛金
  - 皇室珐琅·贵族伊丽莎白
  - 皇室珐琅·国王曜石黑
  - 皇室珐琅·贵族玫瑰粉
  - 国礼非遗·珐琅帝王绿
  - 国礼非遗·珐琅宫廷红
- V1 智能腕表正式产品目录包含 1 款：健康腕表。
- 腕表历史产品“玫瑰”“满天星”“黑金”分别作为独立的“历史停用”腕表产品迁移，保留原始名称、稳定产品 ID、来源记录和当前库存，不映射或并入“健康腕表”。
- 历史停用产品继续出现在库存查询和管理员对账中，并明确显示“历史停用”标识，但不得出现在正常领用、临时领用或线下登记的可选商品列表中；如未来需要重新归类，只能通过有审计记录和库存流水的调整处理。
- 现有指环飞书表中的历史简称必须通过别名映射关联正式产品，历史记录不改名：
  - 黄金款 → 领袖江山·指定乾坤钛金
  - 钻石款 → 巴黎经典·星钻永恒玫瑰金
  - 昆仑款 → 商务精英·间金昆仑灰
  - 蓝宝石款 → 御路荣升·蓝宝石星空
- 系统页面、查询和新业务记录统一使用正式产品名称；历史记录迁移至标准化新表时转换为正式产品名称，同时保留原始名称快照和旧记录关联。
- 智能指环的库存最小单元为“指环款式 + 尺码”，V1 尺码固定为 6# 至 13#。
- 智能腕表的库存最小单元为“腕表产品”，尺码字段不适用且不得要求用户填写。
- 每个产品/款式必须支持配置产品名称、商品大类、启用状态、一张必填主图和多张可选详情图；领用选择、库存查询和详情页均可查看对应产品图片。
- 飞书多维表格附件字段是 V1 唯一图片源，不额外引入对象存储；系统管理员在后台上传、替换和排序图片，后端负责刷新飞书临时下载链接。
- 领用界面按商品大类切换填写方式：指环使用“款式 × 尺码”矩阵，腕表使用产品列表与数量。
- 两套现有飞书多维表格继续作为各自商品大类的最终库存底账。
- 允许在现有多维表格中新增表和字段，并按实际需求优化结构，但必须保留全部历史数据，不删除、不重命名现有字段。
- 不直接在旧表中批量覆盖历史记录；分别在现有指环、腕表多维表格应用内创建标准化新表组，完成历史迁移、核对和切换后，将旧表设为只读归档。
- 标准化新表至少覆盖产品资料、仓库库存余额和库存流水，并按业务设计补充申请主单/明细或必要关联字段。
- 历史记录导入新表时补充稳定业务 ID、正式产品 ID、正式产品名称、原始名称快照、旧表 ID、旧记录 ID、迁移批次和迁移时间。
- 两套旧表中的全部历史出入库记录和现有库存均归属余杭仓；迁移时统一写入余杭仓维度，不再逐条判断仓库。
- 西湖仓不继承或复制任何历史库存，初始数量默认为零；上线后的库存只能通过余杭仓调拨、正式入库或有流水的盘点建账形成。
- 历史迁移脚本必须可重复执行且不重复导入；每批迁移完成后核对源记录数、目标记录数、数量合计及关键维度余额。
- 当前迁移基线为：腕表入库 326 件、出库 61 件、有效库存 265 件；其中健康腕表 128 件，玫瑰 27 件，满天星 42 件，黑金 68 件。腕表入库表另有 2 条全空白记录，台账另有 6 条零值空白记录，迁移时作为数据质量异常留报告但不生成库存业务数据。
- 当前指环迁移基线为：入库 2,984 件、出库 828 件、有效库存 2,156 件；按历史款式为黄金款 316 件、钻石款 520 件、昆仑款 874 件、蓝宝石款 446 件。台账另有 2 条零值空白记录，迁移时留报告但不生成库存业务数据。
- 新旧表核对通过前，网页不得切换到新表；切换后所有新增业务只写标准化新表，旧表停止新增记录但继续保留查询和回滚依据。
- 新增字段应优先用于仓库标识、业务单号、记录来源、商品关联、同步状态、幂等键和关联流水等可追溯能力。
- 网页展示的可用库存必须与飞书底账保持一致。
- 任何库存余额变化都必须对应一条不可缺失的库存流水，禁止只改余额。

### R2. 仓库与二维码入口

- V1 内置西湖仓和余杭仓，并允许后续通过基础资料新增或停用仓库。
- 库存余额与库存流水必须包含仓库维度，同一商品在西湖仓和余杭仓分别核算。
- 所有已通过公司飞书登录的用户均可分别查询西湖仓、余杭仓的准确产品库存，也可查看两仓汇总；角色权限不限制库存数量查看。
- 每个仓库拥有稳定、长期有效的专属页面地址和二维码。
- 领用人扫描仓库二维码后，进入已绑定该仓库的申领页面；登录完成后仍需保留原二维码指定的仓库上下文。
- 二维码入口提供正常领用和临时领用两个明确选项。
- 二维码本身不直接包含账号、库存数量或其他敏感数据，只包含稳定的仓库入口地址。

### R3. 正常领用

- 申请字段包括：来源仓库、领用人、领用类型、用途/对象、商品明细、最终去向、备注，以及按业务条件出现的归还方式和预计归还日期。
- 来源仓库由专属二维码入口自动带入并默认锁定，避免误选仓库。
- 领用人由当前飞书登录身份自动带入，不允许普通领用人冒用其他员工身份提交；仓库管理员线下代录除外。
- 一张正常领用申请允许同时包含智能指环和智能腕表，但所有商品必须来自同一仓库并使用同一领用类型、用途/对象、最终去向和审核流程。
- 混领界面按智能指环和智能腕表分区展示：指环明细填写款式、尺码和数量，腕表明细填写产品和数量。
- 申领页面直接展示二维码对应仓库的具体可用库存数量，提交和审核时仍由后端重新校验。
- 领用类型包括：内部领用、外部赠送、销售、展品。
- 展品必须标记为需要归还，并填写明确的预计归还日期。
- 内部领用可选择“不需要归还”或“需要归还”；选择需要归还后，必须选择“指定日期归还”或“员工离职时归还”。
- 内部领用选择指定日期归还时必须填写预计归还日期；选择员工离职时归还时不要求固定日期，但必须绑定实际领用人的飞书员工身份。
- 外部赠送和销售默认不归还，不显示归还日期字段。
- 系统在提交时校验当前仓库可用库存，在审核通过时再次校验并锁定可发放数量。
- 正常领用采用整单审核和整单发放，不提供商品明细级部分通过、部分拒绝或部分发放。
- 任一商品明细库存不足或信息不合格时，仓库管理员退回整张申请，由申请人调整后重新提交。
- 流程为：提交申请 → 仓库管理员一道审核 → 审核通过并锁定数量 → 确认发放 → 写入对应仓库的飞书库存流水并更新库存。
- 审核拒绝时不得扣减库存，记录需保留拒绝状态和审核痕迹。
- 发放必须是审核后的独立业务动作，只有完成发放才产生领用出库流水。

### R4. 临时领用

- “临时领用”作为正式业务名称，替代此前的“极速领用”表述。
- 临时领用当下只要求来源仓库、领用人和商品数量明细；指环选择款式与尺码，腕表只选择产品。
- 一张临时领用单同样允许混合选择智能指环和智能腕表，但所有商品必须来自二维码绑定的同一仓库。
- 临时领用提交时整单校验库存；任一明细库存不足时整单提交失败，不对其他明细进行部分扣减。
- 来源仓库由二维码自动带入，领用人由当前账号自动带入。
- 提交后立即形成记录、扣减对应库存并写入飞书流水，状态为“待补手续”。
- 后续允许补充领用类型、用途/对象、最终去向和备注等完整信息。
- 信息补齐后进入仓库管理员一道审核；审核通过后状态变更为“已完成”。
- 临时领用因实物和库存变更已经发生，审核不提供直接作废出库的“拒绝”动作；信息不合格时退回“待补正”，由领用人继续修改。
- 后台必须有独立的“待补手续”列表。
- 临时领用的后补审核不得再次扣减库存。

### R5. 线下登记

- 管理员可以代录已在线下发生的领取，无需员工再提交线上申请。
- 每条领用记录必须标记来源：线上正常申请、线下登记或临时领用。
- 线下登记由具备对应仓库权限的仓库管理员填写并直接完成出库，不再进入一道审核。
- 线下登记必须填写完整的领用信息和商品明细，提交时校验对应仓库库存，并立即扣减库存、生成飞书流水。
- 线下登记整单校验和扣减，任一明细失败时不得留下部分成功的库存变动。
- 线下登记记录需保存代录管理员、实际领用人、来源仓库、提交时间和来源“线下登记”。
- 现场信息尚不完整时必须使用临时领用流程，不能以残缺的线下登记绕过待补手续和后续审核。

### R6. 一道审核

- 系统只提供一道业务审核，不设计多级审批链。
- 一道审核由具备仓库管理员角色的账号执行，审核人与发放/登记管理员不再拆分为不同角色。
- 正常领用先审核、后发放。
- 临时领用先领取并扣减库存，后补资料、后审核；资料不合格时退回补正而非撤销历史出库。
- 每次审核必须记录审核人、审核时间、审核结果和审核意见。

### R7. 库存业务与流水

- 入库：增加库存并生成入库流水。
- 领用：减少库存并生成领用出库流水。
- 归还：只有仓库管理员确认实物已归还并选择入库仓库后，才增加库存并生成归还流水；预计日期到达或员工离职不能自动增加库存。
- 调拨：用于西湖仓与余杭仓之间的库存移动，生成来源仓调出与目标仓调入两条关联流水，调拨总量不得凭空变化。
- 盘点调整：对指定仓库生成盘盈或盘亏流水，并按盘点结果调整库存。
- 每条流水至少可追溯到业务类型、业务单据、仓库、商品大类、产品/款式、可选尺码、变动数量、变动前后数量、操作人和发生时间。
- 每一次库存变化先在本地业务事务中生成唯一业务单号、流水明细和飞书同步任务，再由后台同步至对应飞书多维表格。
- 每条飞书同步任务和明细必须带稳定幂等键；自动重试、人工重试或服务重启不得重复扣减或重复生成流水。
- 飞书同步失败时，真实业务记录保留为“已出库/已入库，待同步”，本地立即锁定或调整可用库存，避免同一库存被再次领用。
- 库存页面在飞书已同步余额基础上叠加本地尚未同步的有效变动，明确标识“含待同步变动”，避免把暂时领先于飞书的数量误认为已落入最终底账。
- 后台自动重试同步；持续失败时生成管理员红色异常待办，并允许有权限的管理员查看错误和执行幂等重试。
- 飞书库存余额与流水均写入成功后，业务单据才从“待同步”变为完整完成。
- 混领单按商品大类生成独立飞书同步任务：指环写入指环库存表，腕表写入腕表库存表；任一侧尚未成功时整张单显示为“部分已同步/待同步”，不能误标为完整完成。
- 永久冲突或数据不一致必须通过补偿流水和对账处理，禁止直接清除同步任务或无流水修改余额。

### R8. 提醒

- 提醒只进入系统内的管理员待办/提醒中心，不通过飞书机器人或其他渠道单独推送给领用人。
- 临时领用后生成“待补手续”管理员待办，由仓库管理员跟进领用人补充资料。
- 临时领用手续必须在提交后的 3 个工作日内补齐。
- 工作日期限按 `Asia/Shanghai` 时区和可配置工作日历计算，避免将周末、法定节假日或调休规则硬编码在业务代码中。
- 超过 3 个工作日后，记录继续保留“待补手续”状态，并进入管理员红色超期待办。
- 超期本身不自动冻结或限制领用人的后续正常/临时申领，由仓库管理员负责线下跟进。
- 待归还记录到期时生成管理员待办，由仓库管理员负责线下跟进。
- 指定日期归还在到期时生成管理员红色待归还任务。
- 员工离职时归还通过飞书员工状态同步或事件发现离职后生成管理员红色待归还任务，并允许系统管理员在异常情况下手动标记离职触发。
- 待归还任务完成必须以仓库管理员确认实物回库和归还流水成功为准。

### R9. 查询与导出

- 管理员可按日期、仓库、领用人、商品大类、产品/款式、尺码、领用类型、状态、最终去向组合查询。
- 库存查询支持西湖仓、余杭仓分别查看和两仓汇总；普通领用人、仓库管理员和系统管理员均可查看具体库存数量，不做角色区分。
- 商品结果可查看对应产品图片；指环按款式和尺码展示准确可用数量，腕表按产品展示准确可用数量。
- 库存数量包含本地有效待同步变动时，所有用户均可看到明确的数据状态标识，避免将待同步数量误认为已经落入飞书底账。
- 查询结果需能查看领用单主信息、款式尺码明细、审核记录和关联库存流水。
- 支持按时间段和当前查询条件导出一个 Excel 文件，固定包含两个工作表：
  - `领用单汇总`：每张业务单一行，包含主单、流程、仓库、领用人、审核、发放、归还与同步状态等信息。
  - `商品明细`：每条商品明细一行，包含业务单号、仓库、商品大类、产品/款式、可选尺码、数量及对应状态。
- 两个工作表使用同一筛选范围和业务单号关联；混领单在汇总表为一行，在商品明细表按指环/腕表明细展开。
- 单条领用记录打印作为后续增强项，不阻塞 V1。

### R10. 权限与审计

- 飞书是 V1 唯一登录认证入口，不提供手机号密码、本地注册、短信验证码、密码找回或钉钉登录。
- 普通浏览器使用飞书网页 OAuth/扫码登录；飞书客户端内网页使用飞书免登流程；两种入口识别为同一飞书用户。
- 系统只允许公司飞书租户内且处于应用可用范围的员工进入，外部租户、个人账号或无应用权限人员不得访问。
- 公司员工首次成功登录时自动创建本地业务用户档案，不需要填写注册表，也不经过管理员审核。
- 首次创建的用户默认角色为普通领用人，可立即通过仓库二维码提交正常或临时领用。
- 本地用户档案保存飞书 `user_id`、`open_id`、`union_id`、租户标识、姓名、头像和必要的组织资料快照，但不保存登录密码。
- 系统角色仍为普通领用人、仓库管理员、系统管理员；飞书只证明员工身份，不自动授予仓库管理员或系统管理员权限。
- 普通领用人通过仓库二维码提交正常/临时领用、补充本人手续并查看本人记录。
- 公司员工离职、停用或被移出应用可用范围后，应无法建立新会话；现有业务记录继续保留其历史身份快照。
- 首位系统管理员通过部署配置预设的唯一飞书员工身份初始化，匹配应同时校验公司租户与稳定用户标识，不按姓名判断。
- 首位管理员初始化仅在系统尚不存在系统管理员时执行；匹配员工首次成功登录后自动获得系统管理员角色，并记录初始化审计日志。
- 完成首位管理员初始化后，部署配置不得继续自动提升其他用户；后续仓库管理员和系统管理员均由已有系统管理员在后台授予或撤销。
- 仓库管理员同时拥有一道审核、确认发放、线下登记、库存业务处理、查询、导出和管理员待办处理能力，但所有操作受仓库授权范围限制。
- 仓库管理员账号可绑定西湖仓、余杭仓或两个仓库，账号与仓库为多对多授权关系。
- 仓库管理员只能查看、审核、发放、登记和调整其获授权仓库的数据，不能通过修改页面参数访问未授权仓库。
- 需要从一个仓库向另一个仓库调拨时，操作账号必须同时拥有来源仓和目标仓权限；否则由系统管理员执行。
- 系统管理员负责账号、角色、仓库授权、商品资料、飞书表映射和同步异常配置，并默认拥有全部仓库的数据与操作权限。
- 领用人、审核/发放/登记操作人等身份必须按本地业务用户档案及其绑定的飞书身份追溯。
- 普通领用人只能操作本人允许操作的记录；管理员可查询和处理授权范围内记录。
- 系统管理员可从已登录过的公司飞书员工中授予或撤销仓库管理员、系统管理员角色，并配置仓库管理员的仓库范围。

## Acceptance Criteria

- [ ] AC1：管理员可维护智能指环款式和智能腕表产品；新增腕表产品不需要修改数据库结构或业务代码。
- [ ] AC1A：系统初始化 10 款正式智能指环和 1 款健康腕表产品目录，四个历史指环简称按确认映射关联正式产品且不修改历史飞书记录。
- [ ] AC1B：产品资料使用飞书附件字段保存一张必填主图和多张可选详情图；管理员可维护，普通用户可正常查看，系统不依赖外部对象存储。
- [ ] AC1C：腕表历史产品“玫瑰”“满天星”“黑金”以三个独立的历史停用产品迁移，库存分别保持 27、42、68 件；库存查询可见但任何领用入口不可选择，且不并入健康腕表。
- [ ] AC2：选择智能指环时显示 6# 至 13# 的“款式 × 尺码”矩阵；选择智能腕表时不显示或要求尺码字段。
- [ ] AC3：每个产品/款式可配置并查询产品图片；产品图片在领用选择、库存查询和产品详情中可见。
- [ ] AC4：西湖仓和余杭仓库存独立核算，管理员可分别查询并在权限允许时查看汇总。
- [ ] AC4A：所有公司飞书用户均可查看西湖仓、余杭仓及两仓汇总的准确可用库存，不因角色不同隐藏数量。
- [ ] AC5：两个仓库分别拥有稳定二维码；扫码、登录后进入绑定仓库的正常/临时领用入口，不会因登录跳转丢失仓库信息。
- [ ] AC6：员工可提交包含多个商品明细的正常领用单，必填信息不完整时不能提交。
- [ ] AC6A：同一张正常或临时领用单可以同时包含智能指环和智能腕表，但只能对应一个来源仓库和一套主单业务信息。
- [ ] AC7：正常领用单审核通过前不能发放或扣减库存；完成发放后，对应仓库的指环或腕表飞书底账库存减少且产生逐明细可追溯的流水。
- [ ] AC7A：正常领用只能整单审核和整单发放；任一明细不满足条件时整单退回调整，不产生部分完成状态。
- [ ] AC8：临时领用仅填写领用人和领用明细即可提交；提交成功后立即扣减二维码对应仓库的飞书库存、生成流水并进入“待补手续”。
- [ ] AC8A：临时领用与线下登记的多条明细按整单事务处理，任一明细库存不足或写入本地业务事务失败时均不得部分扣减。
- [ ] AC9：临时领用补齐资料后可以完成一道审核，审核过程不重复扣减库存；资料不合格时退回补正，不撤销已经发生的出库流水。
- [ ] AC10：管理员可以单独筛选全部“待补手续”记录，并能识别超期记录。
- [ ] AC11：管理员可代录线下领用，记录来源在详情、查询和导出结果中均明确可见。
- [ ] AC11A：线下登记由获授权仓库管理员提交后直接扣减库存并生成流水，不产生待审核节点；信息不完整时无法按线下登记提交。
- [ ] AC12：入库、领用、归还、两仓调拨和盘点调整均产生库存流水；不存在无流水的余额修改入口。
- [ ] AC13：管理员可按日期、仓库、领用人、商品大类、产品/款式、尺码、领用类型、状态和最终去向组合查询。
- [ ] AC13A：普通领用人在扫码申领和库存查询页面可查看具体库存数量；权限差异只限制审核、发放、调整等操作。
- [ ] AC14：管理员可按时间段和当前筛选条件导出 Excel，文件同时包含 `领用单汇总` 与 `商品明细` 两个工作表，且可按业务单号核对。
- [ ] AC15：仓库管理员可在系统内集中查看待补手续、超期未补和待归还到期提醒；系统不要求向领用人发送飞书或其他个人消息。
- [ ] AC15A：临时领用提交后 3 个工作日未补齐时进入管理员红色超期待办，但不自动冻结该领用人的申领权限。
- [ ] AC15B：展品必须填写预计归还日期；内部领用可选择不归还、指定日期归还或员工离职时归还；销售与外部赠送不要求归还。
- [ ] AC15C：日期到期或员工离职只生成管理员待归还任务，不自动增加库存；管理员确认实物回库后才生成归还流水。
- [ ] AC16：飞书同步失败时系统不得把未成功落入最终底账的库存变更展示为已完成，并保留可诊断、可重试的失败记录。
- [ ] AC16A：飞书暂时不可用时，已经发生的临时领用、线下登记、发放、归还或调拨保留为待同步，本地可用库存立即反映该变动，用户重复提交不会产生第二次库存变化。
- [ ] AC16B：同步任务自动或人工重试使用同一幂等键；飞书余额和流水均成功后才完成，永久冲突只能通过有流水的补偿或对账解决。
- [ ] AC16C：混领单分别同步两套飞书底账，只有指环与腕表相关任务全部成功后整张单才显示完整完成。
- [ ] AC17：系统仅包含普通领用人、仓库管理员和系统管理员三类角色；仓库管理员可以完成审核、发放和线下登记全流程。
- [ ] AC18：西湖仓与余杭仓之间的调拨产生一出一入的关联流水，调拨前后两仓库存总量保持一致。
- [ ] AC19：现有飞书字段和历史数据保持不变；系统优化只通过新增字段、新增表和兼容映射完成。
- [ ] AC19A：指环、腕表旧表的全部历史记录均迁移到各自标准化新表，历史简称转换为正式产品名称，同时保留原始名称和旧记录关联。
- [ ] AC19B：迁移重复执行不产生重复记录，且源/目标记录数、数量合计和可核对库存余额通过迁移报告验证后才允许切换。
- [ ] AC19C：切换后旧表只读保留，新增业务只写标准化新表；如验收失败可切回旧表且不丢失迁移前数据。
- [ ] AC19D：全部旧表历史记录和当前库存迁移到余杭仓；西湖仓初始库存为零，未经调拨、入库或盘点流水不得出现库存数量。
- [ ] AC20：仓库管理员只能访问其绑定仓库的数据；绑定两仓的管理员可处理两仓，系统管理员默认可访问全部仓库。
- [ ] AC21：后端对每个仓库相关接口执行权限校验，不能仅依赖前端隐藏入口阻止越权访问。
- [ ] AC22：系统不展示任何本地注册、密码登录、短信验证、密码找回或钉钉登录入口，飞书是唯一认证方式。
- [ ] AC23：公司飞书租户内且处于应用可用范围的员工首次登录自动创建普通领用人档案，无需管理员审核即可申领。
- [ ] AC24：外部租户、个人账号或不在应用可用范围内的飞书用户不能进入系统。
- [ ] AC25：飞书普通浏览器 OAuth、扫码登录和客户端内免登最终识别为同一本地业务用户，并保留二维码指定的仓库上下文。
- [ ] AC26：飞书登录不自动授予仓库管理员或系统管理员角色；高权限角色只能由已有系统管理员配置。
- [ ] AC27：本地数据库不保存用户登录密码，但保留飞书身份标识、业务角色、仓库授权和历史操作人快照。
- [ ] AC28：系统无管理员时，只有部署配置中指定且租户与稳定用户标识均匹配的飞书员工首次登录可初始化为系统管理员。
- [ ] AC29：首位管理员初始化完成后，修改部署配置或其他员工登录不能再次触发自动提权；所有后续角色变更均由系统管理员操作并留审计记录。

## Out of Scope

- 复杂经营统计、可视化数据大屏和自定义报表。
- 多级审批、会签、加签、转审等复杂工作流。
- 单条领用记录打印，暂列后续增强。
- V1 以外的复杂仓库管理能力，如采购、供应商、成本核算、批次、序列号和库位优化，除非后续确认现有飞书底账已依赖这些字段。
