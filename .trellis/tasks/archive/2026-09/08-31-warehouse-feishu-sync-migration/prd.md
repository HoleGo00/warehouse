# 飞书库存同步与历史迁移

## Goal

通过官方 `lark-cli` 将 PostgreSQL 中已经确认发生的库存流水可靠同步到指环、腕表两套飞书 Base，并在不删除、不改写旧表的前提下建立标准化产品、余额和流水 V1 表，完成可重复的历史迁移、实时对账与可回滚切换，使飞书继续作为最终库存底账。

## Background

- 前六个业务子任务已经合并到 `main`。所有库存变化均在本地事务中生成 `InventoryMovement`、`OutboxJob`、按商品大类拆分的 `OutboxJobStep` 和审计记录。
- 本地余额使用 `confirmedFeishuQuantity + pendingMovementDelta` 表达飞书已确认数量与待同步有效变动；业务事实不会因飞书暂时不可用而回滚。
- 数据库已预留 `MIGRATION_OPENING`、`MIGRATION`、`RECONCILE_INVENTORY`、`FeishuMapping`、同步状态和管理员 `SYNC_EXCEPTION` 任务类型，但尚未实现 outbox 消费器、CLI Gateway、历史迁移器或真实 Base 写入。
- 本机官方 `lark-cli@1.0.91`、profile `glorychips-warehouse` 和应用/用户身份当前可用；CLI 提示存在更新版本，本任务规划阶段不升级或切换 profile。
- 两套旧 Base 仍在被实际使用。2026-09-04 的实时只读快照显示，指环出库表已由 2026-08-28 审计时的 523 条增加到 547 条，因此迁移不能继续以固定 691 条源记录作为最终切换基线。
- 当前实时数量为：指环 2,984 入 / 866 出 / 2,118 余额；腕表 326 入 / 61 出 / 265 余额。两套台账均与历史入库减出库零差异。
- 2026-08-28 之后新增 24 条指环出库，共 38 件，发生日期为 2026-08-28 至 2026-08-31；它们必须进入最终迁移，不能按旧快照遗漏。
- 2026-09-04 已确认正式切换允许旧 Base 短暂停写。切换采用冻结 revision、捕获最后增量、零差异对账后再激活 V1 映射的低风险路径，不实施持续双写协调。

## Requirements

### R1. CLI Gateway and configuration

- Worker 只能通过受控 `lark-cli` Gateway 访问 Base，不在业务服务中散落 `child_process` 调用或直接使用另一套飞书 SDK。
- Gateway 固定显式传入 profile、身份、Base token、table ID、超时和 JSON 输出格式；密钥继续由 CLI profile 保存，不写入仓库、数据库或日志。
- 启动时校验 CLI 可执行文件、版本、profile、身份和目标表映射；生产环境缺少任一关键配置时同步 worker 必须拒绝启动。
- 测试使用可编程 fake Gateway；真实 CLI 测试限定在受控测试表和正式 dry-run，不让普通单元/集成测试写入正式 Base。

### R2. Standardized V1 tables

- 在指环、腕表各自现有 Base 内新增产品资料、仓库库存余额、库存流水 V1 表；不得删除、重命名或批量覆盖旧表及旧字段。
- 两套表使用一致的稳定字段语义：本地实体 ID、业务单号、幂等键、仓库 ID、产品 ID、正式名称、原始名称快照、可选尺码、数量变化、变化前后值、业务来源、操作人快照、发生时间、旧表/旧记录来源和迁移批次。
- 余额表按 `warehouseId + variantId` 唯一；流水表按本地 movement 幂等键唯一；产品表按本地 product/variant 稳定 ID 唯一。
- V1 新表创建与字段校验必须可重复执行；同名错误结构、字段类型漂移或不可写公式字段必须阻断写入并进入明确的配置错误。

### R3. Outbox processing and idempotency

- Worker 使用 PostgreSQL 行锁或等价的 `SKIP LOCKED` 领取到期任务，设置租约、worker ID、尝试次数和下一次可用时间，进程崩溃后可回收超时任务。
- 每个 `OutboxJobStep` 只处理一个商品大类 Base。混领单允许一侧成功、一侧重试，但主单只有全部必要 step 成功后才为 `SYNCED`。
- 一个 step 必须先幂等写入全部流水，再按 Base 中可验证的当前状态更新对应余额；流水与余额都成功并回读一致后才标记成功。
- CLI 超时或返回不确定结果时，重试前按幂等键查询远端记录；已经存在且内容一致则接续，不一致则进入人工处理，禁止盲目新增第二条流水。
- 可重试错误使用有上限的指数退避和抖动；权限、表结构、字段类型、幂等内容冲突或持续超过阈值的错误进入 `MANUAL_REVIEW` 并创建/更新一个管理员红色同步异常任务。
- 人工重试只能重新激活原 job/step，不得创建新业务流水、清除失败证据或改变幂等键。

### R4. Balance confirmation and reconciliation

- step 成功后，在同一 PostgreSQL 事务中将相关 movement 标记为 `SYNCED`，把已同步 delta 从 `pendingMovementDelta` 转入 `confirmedFeishuQuantity`，并更新关联单据的汇总同步状态。
- 更新前必须锁定相关本地余额并验证 pending delta 能完整覆盖本批 movement；并发完成的不同 step 不得丢失或重复结转。
- 周期性或手动对账按 Base、仓库和 variant 比较远端余额、本地已确认余额、待同步 delta 和本地有效数量，并持久化 `InventoryReconciliation`。
- 自动同步只处理可证明一致的远端前置状态。永久差异通过补偿流水或明确迁移批次解决，禁止无流水直接改本地或飞书余额。

### R5. Historical migration

- 每次迁移先对六张旧表重新执行只读全量快照，保存表 revision、记录数、记录 ID 和数量摘要；最终迁移基线以切换前冻结快照为准，而不是固定 691 条。
- 旧表全部有效历史记录统一迁入余杭仓；西湖仓余额为零，不复制任何历史数量。
- 指环历史简称映射到已确认的正式产品；腕表“玫瑰”“满天星”“黑金”分别迁为历史停用产品，不并入健康腕表。
- 历史入库和出库各生成可追溯的 `MIGRATION` movement；需要补齐当前余额而无法恢复严格时间顺序时，使用有明确来源与报告的 `MIGRATION_OPENING`，不得伪造人员、用途或发生时间。
- 全空白零值记录只进入数据质量报告，不生成产品、余额或流水；其他缺失字段保留原始空值和来源记录。
- 2026-09-08 用户确认指环出库记录 `recvuAsBLXpK1h` 为误建空行；仅在来源身份和已确认完整内容指纹均匹配、业务字段仍为空时，保留日期及来源并记为异常，不生成库存流水。不得扩展为自动忽略所有仅含日期的记录，原记录不删除、不改写。
- 迁移批次按 `sourceTableId + sourceRecordId` 和稳定 migration key 幂等；同一冻结快照复跑新增零条远端记录和零次本地余额变化。

### R6. Dry-run, cutover and rollback

- 正式写入前先在隔离测试表完成 schema、批量写入、查询、超时重试、崩溃恢复和幂等复跑验证。
- 正式 Base dry-run 只读取和生成计划，列出待创建表/字段、待迁移记录、异常记录、预期数量、预计批次数和差异，不执行写操作。
- 切换必须有明确的源表 revision 栅栏。冻结快照之后若旧表继续产生新记录，必须重新捕获增量并重新对账，不能使用过期报告直接切换。
- 第 7 子任务在正式 Base 创建 V1 表并完成一次影子历史迁移、回读和零差异验收，绑定状态保持 `PREPARED`；生产网页的最终激活、业务开放和回滚演练属于第 9 子任务。
- 第 9 子任务切换时先由业务侧短暂停写旧表，再运行最终增量追平；冻结期间任一旧表 revision 变化都使本次切换失败并要求重新生成快照。
- 新旧数量、记录映射、每个产品/尺码余额和 V1 查询全部通过后才切换表映射；旧表保留且停止新增，作为查询和回滚依据。
- 回滚只切回读取/写入映射并暂停新 worker，不删除 V1 表或迁移记录；切换后已经进入 V1 的新业务必须通过对账和补偿方案处理，不能反向覆盖旧历史。

### R7. Administration and visibility

- 系统管理员可查看同步 job/step、目标 Base、业务单号、错误代码、尝试次数、下一次重试时间和最近错误，并执行幂等重试。
- 普通用户只看到业务语义状态，例如“库存同步中”“部分已同步”“同步异常”，不展示 CLI 命令、profile、token、Base token 或原始异常堆栈。
- 本子任务提供同步异常与对账所需的后端契约和最小管理入口；复杂组合查询与 Excel 导出仍属于第 8 子任务。

### R8. Audit and security

- schema 创建、迁移批次、切换、回滚、人工重试、人工解决差异和配置变更全部写入本地审计日志。
- 日志和持久化错误必须脱敏，不记录 CLI 安全配置、用户 token、一次性授权信息或完整个人数据。
- 正式 Base 的创建/写入只在用户批准实施后的受控阶段执行；删除旧表、删除字段、删除记录和不可逆权限变更始终不在本任务自动执行范围内。

## Acceptance Criteria

- [x] AC1：两套 Base 各存在结构一致、可重复校验的产品、余额、流水 V1 表，旧表和旧字段未删除、未重命名、未批量覆盖。
- [x] AC2：正常领用、临时领用、线下登记、入库、归还、调拨和盘点产生的 outbox 可由 worker 同步，余额与流水均回读一致后才成功结转本地 pending delta。
- [x] AC3：混领单按指环/腕表 step 独立重试，允许部分同步；全部必要 step 成功后主单才为 `SYNCED`。
- [x] AC4：CLI 超时、限流、worker 重启、租约回收、自动重试和人工重试均不产生重复流水或重复余额变化。
- [x] AC5：永久权限/结构/内容冲突进入 `MANUAL_REVIEW` 和唯一红色管理员任务，错误可诊断且敏感信息不泄露。
- [x] AC6：历史迁移覆盖最终冻结快照中的全部有效记录；空白零值记录只进异常报告，全部记录可追溯到旧表和旧记录。
- [x] AC7：当前已确认数量基线至少包含指环 2,984 入 / 866 出 / 2,118 余额和腕表 326 入 / 61 出 / 265 余额；最终验收使用切换时新鲜快照重新计算，不把这些规划数字当作永久常量。

- [x] AC10：测试 Base 完成写入与故障恢复验收，正式 Base dry-run 报告通过后才允许真实写入和切换。
- [x] AC11：切换和回滚都有 revision 栅栏、审计和结构化报告；验收失败时可暂停 worker 并切回旧映射，旧数据不丢失。

## Out of Scope

- 删除旧表、删除旧字段、清理旧记录或自动执行不可逆的 Base 权限变更。
- 飞书机器人、短信、邮件或个人消息提醒。
- 复杂组合查询、Excel 导出和完整同步异常后台，留给第 8 子任务。
- 生产部署、V1 绑定激活和最终业务切换/回滚演练，留给第 9 子任务；本任务完成可执行切换工具、正式 V1 表创建、影子历史迁移和一次迁移验收。
- 将 `lark-cli` 替换为另一套 SDK，或升级/切换现有 CLI profile。
